# Self-hosting on Dokploy

Kiki runs on Dokploy on the Proxmox VM `wunet` (VM 100, 192.168.1.38), with the
dashboard at https://dokploy.carltonwu.com behind Cloudflare Access. This replaces
Railway (`.railway/railway.ts`, `tools/railway-sync-env`), which stays in the repo
until Railway is shut down.

## Layout

One Dokploy project, `kiki`, environment `production`, three services:

| Service    | Dokploy kind      | Image                                  | Exposed |
|------------|-------------------|----------------------------------------|---------|
| `postgres` | Database (Postgres) | `pgvector/pgvector:pg18-trixie`      | no      |
| `ingester` | Application (Docker) | `ghcr.io/carltonwu/kiki-ingester:<sha>` | no |
| `agent`    | Application (Docker) | `ghcr.io/carltonwu/kiki-agent:<sha>`    | no |

Each is its own Swarm service, deployed, restarted and logged on its own. They talk
over Dokploy's internal overlay network by app name (`AGENT_HOST_URL` is
`http://kiki-agent-<suffix>:8081`; `DATABASE_URL` points at `kiki-postgres-<suffix>`).
Nothing has a domain: the ingester only dials out (Discord Gateway, OpenRouter) and
the agent is private to the ingester. Health endpoints are checked inside the
container (the images' `HEALTHCHECK`), not through Traefik.

Why not one Docker Compose app: separate applications deploy independently (an
agent-only change never restarts the Gateway connection), and Swarm's rolling
update with health checks works per service.

### Deploys and migrations

Railway ran `ingester migrate` as a pre-deploy step. Dokploy has none, so the
ingester runs with `MIGRATE_ON_START=true` and migrates before serving. Both apps
update **start-first**: Swarm starts the new task, waits for its health check,
then stops the old one (the old ingester gets 30 s to save its Gateway session and
release the leader lock, as `drainingSeconds` did). A task that never turns
healthy, for example after a failed migration, is rolled back to the previous
image.

The ingester deploys before the agent, so the agent starts against the new schema.

## Secrets

| Where | What |
|-------|------|
| Dokploy, environment-level variables | Shared by both apps: `DISCORD_BOT_TOKEN`, `AGENT_HOST_TOKEN`, `OTEL_EXPORTER_OTLP_HEADERS`, `DATABASE_URL`, `AGENT_HOST_URL`, `KIKI_ENVIRONMENT`, the OTLP endpoint. Apps reference them as `${{environment.NAME}}`. |
| Dokploy, app variables | Each app's own: `OPENROUTER_CHAT_API_KEY`, `REDDIT_*` (agent); `OPENROUTER_DECISION_API_KEY`, `GITHUB_*` (ingester); plus non-secret settings. |
| Local `.env` | The source you edit. `tools/dokploy/apply` pushes it (it never prints secret values). |
| GitHub, `production` environment | Only what CI needs to deploy: `DOKPLOY_API_KEY`, `CF_ACCESS_CLIENT_ID`, `CF_ACCESS_CLIENT_SECRET` (secrets) and `DOKPLOY_URL` (variable). Restricted to `main`. |

No runtime secret goes to GitHub, and images carry none, so they're public on
GHCR (the repo is public) and Dokploy pulls them without registry credentials.
`DATABASE_URL`'s password is generated by `apply` and only lives in Dokploy.
`AGENT_HOST_TOKEN` is generated once and kept.

Dokploy stores variables unencrypted in its own Postgres on the VM. That's the
same trust boundary as the VM itself. If that's ever not enough, Dokploy can
read them from Infisical or Vault at deploy time instead.

### Changing a setting or secret

    # Non-secret settings: edit APPS / SHARED_PLAIN in tools/dokploy/apply.
    # Secrets and tunables: edit .env (same keys as before).
    export DOKPLOY_URL=http://192.168.1.38:3000   # on the LAN, skips Cloudflare Access
    export DOKPLOY_API_KEY=...                    # Dokploy > Settings > Profile > API keys
    tools/dokploy/apply           # dry run
    tools/dokploy/apply --apply   # write and redeploy the apps whose env changed

`apply` overwrites what's set in Dokploy's UI for these apps. Make changes here,
not in the UI.

## CI/CD

`.github/workflows/ci.yml` on a push to `main`:

1. Runs every check (python, rust, sim, iac).
2. `changes` picks the services the push touched (`services/ingester/**`,
   `Cargo.*`; `services/agent/**`).
3. `images` builds those with Buildx (GitHub Actions cache) and pushes
   `ghcr.io/carltonwu/kiki-<service>:<sha>` and `:main`, with
   `KIKI_VERSION=<sha>` baked in for telemetry and fault reports.
4. `deploy` (environment `production`) runs `tools/dokploy/deploy`, which, per
   service, sets the app's image to the new SHA, starts a Dokploy deploy, and
   waits until a container on that image reports healthy. It fails the run
   otherwise.

Running the workflow by hand (Actions > CI > Run workflow, on `main`) rebuilds
and deploys both services.

Rollback: re-run an older `main` run's `deploy` job, or set the app's image to
an older `:<sha>` in Dokploy and deploy.

### One-time GitHub and Cloudflare setup

1. Cloudflare Zero Trust > Access > Service credentials > Service tokens: create
   `github-ci`. On the `dokploy.carltonwu.com` application, add a policy with
   action **Service Auth** that includes that token.
2. Dokploy > Settings > Profile > API/CLI Keys: create a key for CI.
3. `gh secret set --env production DOKPLOY_API_KEY`, `CF_ACCESS_CLIENT_ID` and
   `CF_ACCESS_CLIENT_SECRET`. (`DOKPLOY_URL` is already a variable there.)
4. After the first push, check that the GHCR packages `kiki-ingester` and
   `kiki-agent` are public (Package settings > Change visibility).

## Backups

Railway kept its own volume backups. On Dokploy, add an S3 destination
(Settings > S3 Destinations; Cloudflare R2 or Backblaze B2 are cheap) and a daily
backup on the `postgres` database with a retention count. Proxmox backups of VM 100
cover the whole VM as well.

## Telemetry

Unchanged: both services export OTLP to Grafana Cloud. `deployment.environment.name`
comes from `KIKI_ENVIRONMENT` and `service.version` from `KIKI_VERSION`, with
Railway's variables as fallbacks. Railway's resource gauges go quiet (no
`RAILWAY_METRICS_TOKEN`).
